# Investigation: failed Auto Release run 28704542427

Date: 2026-07-13  
Issue: DOT-880 (`237110e7-8587-4515-8fe5-b003ad86c720`)  
Repository: [eiei114/pi-producthunt](https://github.com/eiei114/pi-producthunt)

## Summary

The **Auto Release** workflow run failed on the final step while **npm publish still succeeded** through a parallel **Publish to npm** run triggered by the same `main` push. The failure is **not** a duplicate-version block and **not** an npm Trusted Publishing failure. Root cause is **trigger/configuration**: the `Trigger publish workflow` step passes a corrupted `GH_TOKEN` value to `gh workflow run`, producing `HTTP 401: Bad credentials`.

## Current release / publish pipeline behavior

1. **Auto Release** (`.github/workflows/auto-release.yml`)
   - Trigger: `push` to `main` when `package.json` changes.
   - Detects semver bump, creates `v<version>` tag, creates GitHub Release, then tries `gh workflow run publish.yml --ref "$TAG"`.
   - Permissions: `actions: write`, `contents: write`.

2. **Publish to npm** (`.github/workflows/publish.yml`)
   - Triggers: `push` to `main` (package files), `v*.*.*` tags, `release: published`, `workflow_dispatch`.
   - Uses npm Trusted Publishing (`id-token: write`; no `NPM_TOKEN`).
   - Skips publish when `npm view name@version` already returns the version.

3. **Overlap on version-bump merges**
   - A merge that bumps `package.json` on `main` can start **both** workflows from one push.
   - Tag creation inside Auto Release can also satisfy the tag trigger, but in this incident the successful publish came from the `main` push trigger before/alongside tag dispatch.

## Cause classification

**Trigger/configuration** (workflow YAML defect), not duplicate-version and not Trusted Publishing.

In `.github/workflows/auto-release.yml`, only the `Trigger publish workflow` step ends with a literal `\n` inside the `GH_TOKEN` expression:

```yaml
env:
  GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}\n
```

The preceding `Create tag and release` step uses a clean token and succeeded (`gh release create`). The corrupted token on the dispatch step matches the observed `HTTP 401: Bad credentials` from `gh workflow run`.

## Minimal safe correction options

Do **not** apply in this investigation slice. Open a follow-up correction issue if approved.

1. **Remove the stray `\n` from `GH_TOKEN` in `auto-release.yml`** (smallest fix; restores explicit `workflow_dispatch` path).
2. **Drop the explicit dispatch step** and rely on existing `publish.yml` triggers (`push` to `main`, `v*.*.*` tags, `release: published`). Lowest moving parts, but less explicit and still allows duplicate concurrent publish attempts on version-bump merges.
3. **Serialize triggers** so only one path publishes per version (e.g. publish only on tag/release, remove `package.json` push trigger on `main`). Larger behavior change; needs maintainer review.

## Residual risks

- Auto Release can show red while npm publish still succeeds, which hides real failures behind a compensating trigger.
- Future version bumps may race two publish workflows unless trigger overlap is addressed separately.
- Re-dispatching publish for `v0.3.1` is unnecessary; npm already has `0.3.1`.
